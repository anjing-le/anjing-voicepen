# VoicePen 发布与更新策略

## 1. 发布模型

- 唯一代码主线：`main`。
- 唯一发布源：`anjing-le/anjing-voicepen` 的 GitHub Releases。
- 唯一更新通道：正式通道；不提供 beta、nightly 或通道选择。
- 分发方式：GitHub Release 安装包和应用内 OTA，不上架 Mac App Store 或 Microsoft Store。
- 更新方式：可以自动检查，必须展示更新要点并由用户确认后才下载安装；不强制更新。

Git push 不等于发布。阶段 commit/push 已获持续授权；创建 tag/Release、上传正式产物、使用付费签名能力仍需发布前单独确认。

## 2. 版本规范

采用语义化版本 `MAJOR.MINOR.PATCH`：

- `PATCH`：兼容的修复与小幅体验优化。
- `MINOR`：兼容的新能力或明显产品改进。
- `MAJOR`：不兼容的配置、流程或支持边界变化。

一次发布中的 `package.json`、`src-tauri/Cargo.toml`、`src-tauri/tauri.conf.json`、Git tag、Release 标题、更新清单和产物元数据必须表达同一版本。首个正式可下载版本的具体编号在发布演练后决定。

## 3. 目标产物矩阵

| 目标 | 安装/分发要求 | OTA 要求 | 发布证据 |
| --- | --- | --- | --- |
| macOS Apple Silicon | Developer ID 签名并公证 | 对应架构更新包与 updater 签名 | 安装、首次启动、升级、配置保留记录 |
| macOS Intel | Developer ID 签名并公证 | 对应架构更新包与 updater 签名 | 对应环境的安装和升级记录 |
| Windows x64 | 可信代码签名 | 对应架构更新包与 updater 签名 | 安装、SmartScreen 表现、升级、配置保留记录 |

应用更新签名不能替代 macOS/Windows 代码签名；代码签名也不能替代 updater 对下载产物的独立验证。

## 4. GitHub Release 内容

每个正式 Release 至少包含：

- 明确的版本号和发布日期
- 面向用户的更新要点，而非 commit 列表堆砌
- 兼容性变化、已知问题及必要操作
- 目标平台安装包
- OTA 所需更新产物、签名与清单
- 可校验的构建来源（对应 commit/tag）

更新要点应能直接供应用展示，至少包含“新增 / 改进 / 修复 / 注意事项”中实际存在的类别。没有内容的类别不必出现。

## 5. OTA 信任链

1. 在隔离且受控的位置生成并保存 updater 私钥；公钥编译进应用。
2. CI 从受保护的 Secrets 获取签名、公证材料，构建各目标产物。
3. 对 updater 产物签名，生成与版本及平台一致的更新清单。
4. 经人工核对后，将 tag、Release notes、安装包、更新包、签名与清单作为同一 Release 发布。
5. 应用从唯一正式端点检查版本，解析用户可见更新要点。
6. 用户确认更新后下载；应用验证平台、版本与签名。
7. 仅在验证成功后进入安装；取消或任一验证失败均继续保留当前版本。

私钥、Developer ID 证书、Windows 签名证书及其密码不得进入仓库、普通 artifact 或日志。密钥轮换意味着信任根迁移，必须作为专门发布变更规划，不能直接替换内置公钥。

当前应用通过编译期环境变量 `VOICEPEN_UPDATER_PUBKEY` 注入 updater 公钥。未注入公钥的开发构建会明确显示更新不可用，且不会访问 Release 更新清单；候选发布流水线必须验证该变量存在并使用与产物签名私钥配对的真实公钥。公钥不是秘密，但它是应用信任根的一部分，变更仍须经过发布审查。

## 6. 阶段门禁

### 阶段提交门禁（直接 push `main`）

1. 确认 `main` 与远端状态，并识别已有未提交变更的归属。
2. 检查 diff，只包含本阶段已批准范围。
3. 执行阶段对应的格式、静态检查、测试和构建。
4. 扫描真实 API Key、私钥、证书、密码及意外构建产物。
5. 更新受影响的架构、技术债或验收记录。
6. 创建单一职责 commit，确认后 push `origin/main`。

### 候选发布门禁

- CI 对目标矩阵全部成功，版本元数据完全一致。
- Release notes 已完成且适合应用内展示。
- 安装包具备目标系统代码签名；macOS 公证成功。
- updater 产物签名和清单验证成功。
- 从上一可发布版本升级的演练通过，配置保持。
- 无更新、稍后更新、网络失败、签名失败、平台不匹配均验证不会损坏旧版本。
- 已知问题与回退方案已记录。

### 正式发布门禁

- 候选发布证据经集中复核。
- 仓库无密钥和无关文件，tag 指向已验证 commit。
- 获得明确的正式 Release 授权。
- 发布后执行一次干净环境下载、安装及应用内更新可发现性检查。

## 7. 回退与故障处理

- 已发布 tag 和产物保持不可变；发现问题时发布新的修复版本，不原地替换同名资产。
- OTA 失败必须终止安装并保留当前可运行版本。
- 严重问题可撤下有问题 Release 的“latest”可见性或记录警告，但不得用未签名资产快速替代。
- 若新版本已安装且需回退，优先发布更高版本号的修复包；直接降级只有在配置兼容性经验证后才能提供明确人工步骤。
- 每次事故记录受影响版本、平台、原因、缓解措施与防复发门禁。

## 8. 暂未满足的外部条件

- Apple Developer ID、公证凭据及其费用/账号归属尚未由仓库证明。
- Windows 代码签名证书、信任级别和保管方式尚未确定。
- updater 私钥的生成、备份、轮换和 CI Secrets 权限尚未实施。
- macOS Intel 与 Windows x64 的真实验收环境尚未建立证据。

在这些条件满足前，可以完成代码和构建流水线准备，但不得声称生产级双端发布或 OTA 验收已完成。
