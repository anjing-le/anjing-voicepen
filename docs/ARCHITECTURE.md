# VoicePen 架构基线

## 1. 当前基线

当前应用采用 Tauri v2 + React + TypeScript + Rust：

- React 负责设置窗口和浮动状态界面。
- Rust 负责录音、全局快捷键、STT/LLM 请求、剪贴板、自动粘贴、托盘、窗口及本地配置。
- 配置写入本机 JSON；AI 请求使用用户提供的 OpenAI-compatible 服务信息。

现有 MVP 已形成完整链路，但多数 Rust 能力集中在 `src-tauri/src/lib.rs`。这是当前事实，不是长期模块边界。

## 2. 目标边界

```text
React UI
  ├─ 设置与首次配置
  ├─ 录音/处理/错误状态
  └─ 更新提示、更新要点与用户确认
          │ Tauri command / event
Rust 应用核心
  ├─ Runtime：明确的录音与处理状态机
  ├─ Audio：采集、归一化与 WAV 编码
  ├─ Provider：STT 与 LLM 接口及 OpenAI-compatible 实现
  ├─ Config：校验、持久化与未来迁移
  ├─ Platform：快捷键、剪贴板、粘贴、权限、托盘与窗口
  └─ Update：检查、展示数据、下载、验签与安装协调
          │
外部边界
  ├─ 用户选择的 STT/LLM 服务
  └─ GitHub Releases 单一更新源
```

模块化的目标是隔离变化与支持测试，而非一次性重写。平台专有实现必须位于显式边界内，避免条件编译散布到业务流程。

## 3. 核心状态机

运行态至少区分：`idle`、`recording`、`transcribing`、`polishing`、`done`、`error`。核心可以使用内部 `completing` lease 保护剪贴板和粘贴副作用，但对前端仍稳定序列化为 `polishing`。后续实现必须满足：

- 同一时刻只有一次录音或处理管线拥有执行权。
- 处理期间的重复快捷键不会启动第二条管线或覆盖有效结果。
- 每个失败路径都回到明确、可继续使用的状态。
- STT 成功而润色失败时，应尽可能保留原始转写，避免已有结果丢失。
- UI 展示态由核心运行态派生，不建立互相矛盾的第二套事实来源。

更新流程拥有独立状态（如检查、可用、下载、安装、失败），不能阻塞正常语音输入；安装重启前必须由用户明确确认。

## 4. Provider 边界

首期继续支持用户配置的 OpenAI-compatible STT `/v1/audio/transcriptions` 与 LLM `/v1/chat/completions`，但领域流程不直接依赖具体 HTTP 形状。

Provider 边界负责：

- 请求构造、鉴权和响应解析
- 超时及可面向用户的错误分类
- 隔离第三方响应，防止敏感信息直接进入日志或界面
- 便于使用模拟实现测试语音处理状态机

Provider 抽象不意味着建设插件市场或动态提供商系统；只实现真实需求所需的最小接口。

## 5. 配置与敏感信息

- 当前 JSON 配置属于既有兼容目标，首期保持其可读性与位置稳定。
- API Key 当前以明文写入本地文件；Unix 上虽然尝试设为 `0600`，权限调用失败会被忽略，Windows ACL 也未经验证。这是已登记风险，不应误称为安全存储。
- 配置模型发生变化时必须设置默认值或迁移策略，避免 OTA 后旧配置使应用无法启动。
- 应用日志、错误事件、测试夹具与提交内容不得包含真实密钥。
- 后续若迁移系统钥匙串，应通过版本化迁移保留现有用户配置，并提供失败回退。

## 6. OTA 架构与信任边界

GitHub Releases 是唯一版本发现与下载来源，但 GitHub HTTPS 本身不是更新信任根。更新信任链为：

```text
受控更新私钥（仅安全环境）
  → 对平台更新产物签名
  → GitHub Release 发布版本、更新要点、产物、签名/清单
  → 应用内置更新公钥
  → 检查唯一正式通道
  → 展示版本与更新要点
  → 用户确认
  → 下载并验证签名
  → 验证通过后安装；失败则保留当前版本
```

约束：

- 更新私钥不得进入源码、构建日志或普通开发机配置；公钥可以随应用发布。
- Release 版本、应用配置版本、安装包及更新清单必须一致。
- 更新检查可自动进行，下载安装不得绕过用户确认。
- 签名缺失、签名错误、版本/平台不匹配时必须拒绝安装。
- Release notes 是产品数据，需要以可读方式呈现；不能只提供一个跳转链接。
- OTA 只使用一个正式通道，不引入通道选择配置。

当前 `Update` 模块只允许固定的 GitHub Releases `latest.json` 地址，由 Rust 持有待安装更新并执行下载、验签与安装；前端只获得可展示的状态和纯文本更新说明。应用启动检查是独立的异步任务，失败只进入更新状态，不改变语音运行状态。没有编译期 updater 公钥时，检查会在联网前安全停止。

应用更新签名与操作系统代码签名解决不同问题，二者都需要：前者保护 OTA 信任链，后者支持 macOS Gatekeeper/公证和 Windows 安装信任体验。

## 7. 可测试性与可观测性

- 纯逻辑（配置校验、版本比较、状态迁移、URL/请求组装）优先单元测试。
- 外部服务、音频设备和平台粘贴通过边界隔离，以模拟对象测试失败与并发路径。
- CI 负责可自动验证的构建与测试；真实设备清单负责麦克风、权限、全局快捷键、粘贴及升级。
- 错误信息应支持用户恢复和开发者定位，同时删除密钥、授权头和不受控的完整第三方正文。

## 8. 架构变更门禁

影响配置兼容、状态机、Provider 契约、支持平台、更新信任根或发布产物的改动，必须同步更新相关文档和技术债记录。引入账号、后端服务、多通道或商店分发属于产品方向变更，不能作为普通实现细节加入。

当前 `csp: null` 仅是已观察到的 MVP 配置，不是目标安全架构。接入 OTA 前必须建立覆盖 UI 资源、用户 Provider 请求与更新端点的最小 Content Security Policy，并用真实功能验证，不能简单复制不受限策略。
